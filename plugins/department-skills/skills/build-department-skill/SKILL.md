---
name: build-department-skill
description: Turn a recurring department job and an example of good work into a reusable skill, a short standard for its lead to confirm, and cases for evaluating future changes.
---

Start with the job in the team's words. Identify who uses the result, the decision or action it supports, and what they should have in hand. Search the existing skills for that output. Extend a matching skill when possible. Reference the team's existing ICP, voice, or other source materials by name wherever another skill already owns them.

## Draft the standard

Use a representative input and an accepted output or a before-and-after edit. If neither is supplied, make a clearly labeled synthetic pair to help the lead decide. Identify which choices change whether the result can be used. Separate fixed requirements from preferences that can vary by audience or assignment.

Show the lead one compact decision in their own language:

- **Job and example** — Show the deliverable and the excerpt that matters.
- **Ready to use when** — List observable criteria. For each, say what would fail, even if the output sounds plausible.
- **When information is missing** — Show one case where the skill should ask, omit a claim, or flag uncertainty.
- **Decision** — Ask the lead to confirm the standard or edit the exact line they disagree with. A simple yes suffices when tied to this version. Keep their response with the standard in the company's own workspace. Leave it marked proposed until confirmed.

Proceed with drafting and testing while confirmation is pending. Never attribute a synthetic example or an inferred rule to a real lead.

## Build and exercise the skill

Produce a folder with a verb-led name and a SKILL.md containing name and description frontmatter, required inputs, steps, output format, and the agreed checks. Put long examples in a referenced file so ordinary runs only need the instructions. State which team materials to read and how to handle a missing dependency.

Supply a runnable request with shareable inputs and a way to judge the answer. Include a case that should pass and a plausible failure that a shallow check would miss. Use deterministic checks for facts that can be calculated. For a judgment such as brand voice, give the reviewer a concrete pair and identify the difference. Report which checks actually ran and which still need evidence.

## Hand off improvements

Identify the point where a completed artifact or its edited version becomes available and the downstream event that would show business use. Name the source for each, or mark it unavailable. Record the skill version with the evidence. Treat an edit as a lead for investigation. Keep quality, actual use, and measured model cost separate. Hand reproducible discrepancies to improve-skill with a regression case. The lead reviews the tested change before it becomes the shared version.
